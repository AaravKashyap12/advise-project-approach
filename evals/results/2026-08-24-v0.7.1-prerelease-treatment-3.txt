Assuming this is a small solo/team MVP with standard web booking flows and no unusual compliance or multi-tenant constraints.

1. Build one end-to-end booking slice around a single provider’s availability calendar: define the minimum models in Django (`Provider`, `Service`, `AvailabilityRule`, `Booking`), expose one server-rendered or API-backed flow where a user can view open slots for the next 7 days and create a booking, and enforce the core invariant in Postgres-backed writes so a slot cannot be double-booked. Acceptance behavior: a real user can open the app, choose a slot, book it, and immediately see that slot disappear from availability. Focused check: create two near-simultaneous booking attempts for the same slot and confirm exactly one succeeds.

2. Add the architecture seam that matters most early: isolate booking decision logic into one Django application boundary or service module responsible for “compute availability” and “create booking transaction,” while keeping views/controllers thin and models simple. Acceptance behavior: both the UI/API endpoint and an admin or internal command path can create bookings through the same booking logic without duplicating rules. Focused check: trace one booking through the code and verify the overlap, validation, and persistence rules live in one place, not repeated across multiple entry points.

3. Prove the system can support normal product change without structural pain by adding one realistic variation, such as service duration differences or provider blackout dates, using the same flow and schema with minimal rewiring. Acceptance behavior: you can add the variation and still book correctly without redesigning routes, duplicating tables, or bypassing the original booking transaction path. Focused check: implement that variation and count the touched areas; if the change stays mostly inside the booking domain module, schema, and a small UI/API adjustment, the architecture is holding.

Escalate only if step 3 forces the same booking invariant to be reimplemented in two places, or if step 1 cannot reliably prevent double-booking under concurrent requests.
