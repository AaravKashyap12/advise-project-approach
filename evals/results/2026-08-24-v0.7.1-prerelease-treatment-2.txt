Assumption: this is a small Django server-rendered product with a single business-critical flow: a customer picks a time slot and creates an appointment.

1. Build the first vertical slice as one end-to-end booking path, not setup in isolation: create the core models for `Service`, `AvailabilityWindow`, and `Appointment`, one form/view/URL that books a slot, and one confirmation page. Acceptance behavior: from a blank database, you can create availability for a provider, submit one booking through the UI, and see the appointment persisted in Postgres with the chosen slot no longer offered. Focused check: one request-level test that posts a booking and asserts exactly one `Appointment` row is created and the returned page shows the booked time.

2. Prove the architecture protects the main invariant before adding more features: put the booking rule in one domain boundary you can call from both the view and tests, and enforce “a slot cannot be double-booked” with a database-backed constraint/transaction strategy rather than only form validation. Acceptance behavior: two near-simultaneous booking attempts for the same slot result in one success and one clean failure, with no duplicate appointments in Postgres. Focused check: one concurrency-oriented test or transaction test that attempts the same booking twice and verifies the invariant holds at the database level.

3. Add the smallest operator loop that shows the design will stay usable: an admin/staff workflow to define weekly availability, view upcoming appointments, and cancel or reschedule one booking. Acceptance behavior: a staff user can create availability, see bookings without manual SQL, and perform one cancellation/reschedule without corrupting slot state. Focused check: one integration test covering “create availability -> book -> cancel/reschedule -> slot becomes correctly unavailable/available again,” plus a short manual walkthrough in Django admin or the staff UI.

Escalation condition: if step 2 becomes awkward because rules are scattered across views, forms, and signals, stop adding features and centralize booking logic into a single application service before proceeding.
