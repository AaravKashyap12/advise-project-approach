1. Build the thinnest end-to-end booking slice: one staff calendar, one service type, public “book appointment” form, server-side availability check, and a persisted `Appointment` row in Django/Postgres. Acceptance behavior: a user can choose a real time slot, submit once, and the appointment appears in an internal staff view with no manual DB work. Focused check: create two simultaneous booking attempts for the same slot and confirm only one succeeds; if both succeed, your domain boundary is wrong and you need to tighten transaction/locking logic before adding features.

2. Add the first operator workflow, not more platform layers: staff can mark availability windows, block time off, and cancel or reschedule an appointment from Django admin or a simple internal view. Acceptance behavior: changing availability immediately changes which slots the public form offers, and rescheduling preserves a clean audit trail in the database. Focused check: change a staff member from available to blocked for a future slot and verify that slot disappears from booking without code changes elsewhere; if slot logic is duplicated across model, form, and view, the architecture is already drifting.

3. Add the first reliability seam around the booking flow: confirmation email or notification, basic idempotency protection on booking submission, structured logging for booking decisions, and one integration test covering the booking transaction. Acceptance behavior: a successful booking produces one appointment, one notification, and one clear log trail; retries or double-clicks do not create duplicates. Focused check: replay the same booking request twice and confirm the system stays consistent without manual cleanup; if consistency depends on view-order quirks instead of model/service invariants, stop expanding features.

Escalate the architecture only if the same booking invariants are duplicated across two entry points or the concurrency/idempotency checks fail under basic parallel request testing.
