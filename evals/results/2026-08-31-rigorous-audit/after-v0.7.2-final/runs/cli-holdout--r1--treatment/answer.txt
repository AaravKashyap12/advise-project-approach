Assumption: this is a local offline CLI over ordinary image files on one filesystem, and you want safety over speed.

1. Build a `plan` mode that scans a chosen folder, reads each photo’s date from metadata when present and falls back to filesystem modified time otherwise, then computes a no-overwrite target name like `YYYY-MM-DD_HH-MM-SS[_NNN].jpg` and prints or writes a preview manifest showing `source -> target` plus the date source used. Acceptance behavior: against a small fixture folder, you can review every proposed rename before anything changes on disk, and any duplicate target names are resolved deterministically with suffixes. Focused check: create 5-10 disposable test files including two with the same timestamp, one without usable metadata, and one already matching the target pattern; verify the manifest contains no duplicate destinations and no file is modified.

2. Add an `apply` mode that only executes from an approved manifest and renames each file with a fail-closed check that refuses if the destination already exists, logging success/failure per file so you can stop on the first conflict instead of risking silent overwrite. Acceptance behavior: running `apply` on the reviewed manifest renames only the listed files, never clobbers an existing file, and leaves a machine-readable log you can compare against the preview. Focused check: in a disposable folder, generate a manifest, then intentionally create one of the destination filenames before `apply`; the run should abort or skip that entry without overwriting anything, and the log should make the blocked rename obvious.

If the focused check in step 2 ever overwrites an existing file or produces a preview that differs from what `apply` attempts, stop and fix the write path before touching real photos.
