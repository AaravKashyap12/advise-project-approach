Use a single-process desktop or local-web app in Python with SQLite. Best fit for two weekends is `Flask` plus server-rendered templates, or `Textual` only if you already know it; otherwise Flask is lower risk because CRUD, forms, and filtering are straightforward. Keep the schema minimal: `recipes`, `tags`, `recipe_tags`, and optionally `recipe_search` using SQLite FTS5 for title, ingredients, and instructions. For 1,000 recipes, SQLite is easily sufficient; the real constraint is build speed, not scale.

Evidence status: no repo was provided, so this is constraint-driven advice only. External comparables and pricing research were not available, which is acceptable here because you explicitly want offline Python + SQLite with no services.

Approach:
1. Build the vertical slice first: create/edit a recipe, attach tags, list recipes, search by text, filter by tag, persist to SQLite.
2. Store canonical recipe data as normalized tables, then add JSON import/export at the boundary. Export one stable schema you also import.
3. Use FTS5 early if you want search to feel good; otherwise start with `LIKE` and switch only if it feels weak. At 1,000 recipes, either works, but FTS5 gives better multi-field search with little added complexity.
4. Keep attachments, auth, sync, mobile, and “smart” features out of scope.

What you gain: fastest path, low maintenance, zero hosting cost, portable local data.
What you give up: multi-device sync and remote access.

First proof: import 100 sample recipes, then verify you can search `"chickpea curry"`, filter by `weeknight`, edit one recipe, export JSON, wipe DB, and re-import without data loss.

This becomes the wrong approach if you later need sync, sharing, or concurrent multi-user access.
