Evidence is limited: the local fixture is empty, so this is advice from your stated direction only, not a repo-specific review.

1. Create one thin vertical slice around the booking write path: `Customer -> Service -> Appointment`, plus one POST endpoint and one simple success page or JSON response. Put the booking rule in one domain location, not scattered across form/view/model hooks: “create appointment only if provider has no overlapping slot.” Acceptance: from a blank database, one valid booking request creates exactly one row and returns a visible confirmation with the saved start/end/provider. Focused check: run two cases against the same endpoint, one non-overlapping and one overlapping, and verify the second is rejected by the write path, not just hidden in the UI.

2. Prove your concurrency boundary early using Postgres transactions on the actual slot-allocation write, typically with `transaction.atomic()` plus a database-backed conflict strategy such as exclusion/uniqueness logic or row locking around the provider/day slot set. Acceptance: when two competing requests try to book the same slot, only one succeeds and the database ends with one appointment. Focused check: use a deterministic concurrent test with two independent transactions synchronized to hit the critical section together; unsynchronized parallel requests are only a stress probe, not proof. If this fails, debug the write path before adding queues, caches, or service layers.

3. Add the minimum architecture feedback loop: one integration test for the happy path, one for overlap rejection, one for concurrent double-book prevention, plus a single admin/report view that lists appointments by provider and day. Acceptance: you can create, reject, and inspect bookings end to end without touching the database manually, and the same invariants hold through tests and the read model. Focused check: reset a disposable database, run the three tests, then manually create a booking and confirm the reporting view reflects it correctly. Escalate only if the same booking invariant starts being duplicated across multiple entry points or you need workflows Django’s normal request/transaction model cannot coordinate cleanly.
