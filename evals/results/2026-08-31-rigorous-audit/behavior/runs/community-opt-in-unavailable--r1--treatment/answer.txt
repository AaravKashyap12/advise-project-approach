### Recommended Stack
- Backend: `Django`
- UI: Django templates, light CSS, minimal JS
- Search: `SQLite FTS5` first
- Content model: handbook entries in DB with title, slug, body, tags, status, updated_at
- Editing: `Django admin`
- Auth: Django built-in auth initially
- Deployment: low-cost VPS or similar single-instance host
- Storage: local disk for MVP if attachments are small; object storage only if needed
- Tests: model/search tests plus one end-to-end smoke path
- Observability: basic error logging and uptime ping

Why this fits:
- Django gives auth, admin, forms, validation, and templating immediately.
- SQLite FTS5 avoids standing up Postgres or a search service too early.
- Server-rendered pages keep build speed high and ops low.
- For 50 staff and a handbook workload, one process and one database file is a reasonable MVP trade.

### Architecture Direction
Keep it as one app first:

```text
Browser
  -> Django views/templates
  -> HandbookEntry model + tags
  -> SQLite database with FTS index
  -> Django admin for editors
```

Key design choices:
- store rendered-safe content in the DB
- keep search indexed on title, summary, body, and tags
- separate published vs draft content
- add simple role separation only if needed: readers and editors

### Alternatives Considered
1. **Django + Postgres from day one**
   Gain: better long-term database tooling, stronger concurrent write story, cleaner later growth.
   Give up: more setup and more hosting friction for a four-week MVP.
   Harder later: nothing major; this is the safer growth path.
   Wrong when: IT already provides managed Postgres cheaply or you know SSO/audit/compliance will land immediately.

2. **Static docs site + Pagefind-style search**
   Gain: very cheap hosting, fast reads, simple deploy.
   Give up: browser-based editing and admin workflow.
   Harder later: non-technical content updates, permissions, drafts.
   Wrong when: only one technical maintainer edits markdown and staff are read-only consumers.

3. **FastAPI/Flask custom app**
   Gain: more control, lighter framework feel.
   Give up: you must rebuild admin/content workflows Django already solves.
   Harder later: content operations and auth ergonomics.
   Wrong when: the handbook is just one small feature inside a broader API-first platform.

### Build Plan
1. Build the first vertical slice: staff can sign in, browse handbook entries, and search by keyword across title/body/tags.
   Acceptance behavior: a user searches a term and gets relevant handbook entries with snippets.
   Focused validation: seed 20 sample entries and verify expected top matches for 5 representative queries.

2. Add editor workflow through Django admin with draft/published states and basic tagging.
   Acceptance behavior: an editor creates a draft, publishes it, and the entry appears in search and browse views.

3. Harden deployment with backups, simple monitoring, and import/export path.
   Acceptance behavior: you can restore content from backup and redeploy without manual DB surgery.

### Validation Plan
Focused first check:
- create representative handbook content with overlapping terms, synonyms, and tags
- verify search returns the expected entry set for known queries
- measure whether typical queries feel instant for your seeded dataset

Broader regression scope after that:
- auth smoke test
- create/edit/publish smoke test
- deployment restart test
- backup/restore check

Escalation signal:
- move off SQLite-first if you hit any of these:
  - search quality is unacceptable even after tuning simple ranking/snippets
  - you need many concurrent editors
  - handbook content grows into large attachments, PDFs, or OCR
  - IT requires SSO, audit logs, or stronger operational guarantees

### Risks and Unknowns
- If staff require corporate SSO now, auth may become the real schedule risk, not search.
- If content includes PDFs or file-heavy manuals, text extraction/search complexity rises quickly.
- If non-technical editors dislike Django admin, you may need a custom editing UI sooner.
- If IT disallows SQLite in production, start with Postgres instead.
