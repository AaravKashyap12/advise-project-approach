Assuming a greenfield Django app with no existing repo constraints, keep the first slice in plain Django apps/models/forms/views/admin and use Postgres directly before adding any service layer or async infrastructure.

1. Build the end-to-end booking slice for one staff calendar: create models for `Service`, `Staff`, `AvailabilityWindow`, and `Appointment`, then ship one user flow that shows open slots for the next 7 days and lets a customer submit a booking. Acceptance behavior: from a browser, you can create availability in admin, visit the booking page, see only valid open slots, submit once, and immediately see the appointment persisted in Postgres. Focused check: add one integration test that seeds availability, posts a booking, and asserts exactly one `Appointment` row is created for the chosen slot.

2. Prove the architecture prevents double-booking before adding more features: enforce slot uniqueness in the database and handle the collision cleanly in the Django request path. Acceptance behavior: if two requests try to book the same staff/time, one succeeds and the other gets a clear “slot no longer available” response, with no duplicate rows. Focused check: write a transactional test that attempts the same booking twice and asserts the database constraint, final row count, and user-visible error path.

3. Add the operator workflow that will expose whether your boundaries are still sane: a staff/admin view to list upcoming appointments, cancel one, and reopen that slot for booking. Acceptance behavior: staff can see today’s bookings, cancel one actionably, and the public booking page shows that slot available again without manual repair. Focused check: one request-level test that books a slot, cancels it through the operator flow, then confirms the slot reappears in the public availability query.

Escalate the architecture only if the same booking rules or availability calculations are duplicated across two entry points or the double-booking/concurrency check cannot be kept correct with model/query logic plus a DB constraint; that is the point to extract a dedicated booking domain module, not earlier.
