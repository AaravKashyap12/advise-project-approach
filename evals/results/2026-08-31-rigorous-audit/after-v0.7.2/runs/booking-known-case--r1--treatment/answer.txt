Assuming a small single-product codebase with one Django app or a very small set of apps, the goal is to prove booking correctness before adding secondary features.

1. Define the booking invariant in the data model first. Create the core tables for `Provider`, `Service`, `AvailabilityRule`, and `Appointment`, and enforce the one rule that matters most at the database boundary: a provider cannot have overlapping active appointments in the same time range. Acceptance behavior: two non-overlapping bookings save successfully, but an overlapping booking for the same provider is rejected even if the request logic misses it. Focused check: write one model-level test that inserts valid bookings and one that proves overlap rejection through Postgres-backed constraints or transaction-safe validation, not just form logic.

2. Build one end-to-end booking path with no admin-heavy detours. Implement a single public flow: list available slots for one provider, submit a booking, persist it, and return a confirmation page or JSON response. Acceptance behavior: a user can start from an empty browser session, choose a visible slot, complete the booking, and immediately see that slot disappear on the next availability read. Focused check: add one integration test that drives the full request cycle against the real Django view, confirms the appointment row exists, and confirms the same slot is no longer offered.

3. Add the earliest concurrency proof before expanding features. Wrap booking creation in a transaction and make the write path the only place that converts a slot into an appointment, then test competing requests for the same slot. Acceptance behavior: when two near-simultaneous booking attempts target the same provider and slot, exactly one succeeds and the other gets a clean conflict response; no duplicate booking appears in Postgres. Focused check: create a deterministic concurrency test or a disposable script that opens two transactions and verifies the invariant holds under overlap, not just under sequential retries.

Escalate the architecture only if this third check fails repeatedly or if the same booking rules start being duplicated across multiple entry points; that is the point where you should consider a clearer domain boundary or a dedicated booking service module.
